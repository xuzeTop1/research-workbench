# 学术防御语态风格参考

通用学术写作防御性表达模式。润色时参照此文档保持语态一致。

---

## 一、限定范围的经典句式

### 研究范围限定

> "本文面向[特定场景/约束]，研究在[限定条件]下……"

> "本文所述[X→Y→Z]是**逻辑关系描述**，当前证据尚未在统一运行时中验证完整链路。"

**模式**：声明范围 → 说明当前证据边界 → 不越界声称

### 实验结论限定

> "实验表明，方法A在[指标1]上优于基线（0.XX vs. 0.YY），但在[指标2]上存在权衡。"

> "在[前提条件，如预计算/离线评测]下，系统在[硬件环境]上的平均耗时为 Z.ZZ ms。"

**模式**：先给前提条件 → 报告数字（不概括为"效果好"）→ 指出 tradeoff 不隐藏

### 贡献声明限定

> "本文提出了[具体机制]，通过[具体手段]实现[具体目标]。"

而非："本文首次提出了一种革命性的方案。"

**模式**：具体做了什么 → 用了什么手段 → 不声明"首次"除非有系统检索证据

## 二、承认局限的句式模板

### 适用边界声明

> "上述结果仅在 [XX 条件] 下成立。对于 [YY 场景]，本文方法可能面临 [ZZ 挑战]，需要进一步验证。"

### 已知局限

> "当前工作存在以下局限：（1）[数据/评测范围局限]，[影响什么结论]尚未验证；（2）[方法假设局限]，[依赖什么外部条件]；（3）[实验条件局限]，[未覆盖什么场景]。"

**模式**：编号列举 → 每条说"是什么+为什么是局限+影响什么结论" → 不给读者"作者自己没意识到问题"的感觉

### 数据/评测口径声明

> "评测基线（N 道有效查询，[口径名] 条件口径）"

> "其中 [排除条件] 因 [具体阈值] 而按 [规则名] 排除"

**模式**：在结果出现前就声明评测条件 → 避免审稿人质疑 cherry-picking

## 三、段落级防御写法

### 方法选择理由（WHY 而非 WHAT）

> "本文选择[方法X]而非[方法Y]，原因在于：[X的关键特性]使得[具体好处]，无需[Y所需的额外步骤]。"

而非："本文使用X进行融合。"

### 与竞品比较的公平表述

> "现有[某类]系统的评测普遍存在[具体机制问题]。在[该条件]下进行的实验，实际上比较的是[A因素]而非[B因素]。"

注意：指出问题但不贬低 → 描述机制 → 让读者自己判断。

### 工程事实 vs 方法论贡献

> 工程描述："系统实现了[具体技术组件]。"
>
> 方法论提升："本文提出了一种在[约束条件]下，通过[设计策略]解决[问题类型]的[方法名]。"

## 四、禁止用语 → 替代对照表

| 想写的（太绝对） | 应该写的（防御性） |
|----------------|------------------|
| 实验证明了本文方法的有效性 | 实验结果支持了本文方法在[具体指标]上的有效性 |
| 该方案解决了XX问题 | 该方案在本评测条件下有效缓解了XX问题 |
| 相比现有方法具有明显优势 | 在[具体条件]下，本方案在[具体指标]上优于对比方法（数字） |
| 这是业内首次将XX应用于YY | 据我们所知，在[检索范围]内，较早将XX应用于YY |
| 保证了数据安全性 | 通过[具体机制]降低了数据泄露风险 |
| 完全兼容现有系统 | 在本文测试的[N]种环境下未观察到兼容性问题 |
| 显著优于（无p值/效应量） | 优于（+X%，配对检验 p=Y）/ 明显高于（定性描述） |

## 五、节级结构惯例

### 引言末段贡献声明模板

```
本文的主要贡献包括：
（1）提出了[方法/架构名]，[解决什么问题]+[关键技术手段]；
（2）建立了[评测/基准名]，[填补了什么空白]+[验证了什么]；
（3）实现了[系统名]，[验证了可行性]+[关键性能指标]；
（4）通过[实验类型]验证了[关键结论的限定表述]。
```

### 讨论与局限的标准三小节

```
X.1 主要发现的启示（不重复实验数字，谈"这意味着什么"）
X.2 适用边界（在什么条件下结论成立、什么条件下可能失效）
X.3 后续方向（具体可做的改进，不用"未来将进一步研究"这种空话）
```
